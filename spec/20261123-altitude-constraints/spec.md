## 概要

SID / STAR を割り当てた航空機は、その機種の性能上限の範囲で、公示された高度制約を満たして飛まなければならない。#146 のレビュー録画では `TIARA3B.RWY16R` が KAMAT を 8937 ft で通過しており、公示は at-or-above 9000 ft である。レビュー側は ±250 ft で `constraintMet: true` としていたが、63 ft の不足は見逃しではない。

現状の垂直誘導は「次のウェイポイントだけ」を見る。制約の無い次フィックスはフライトプランのクルーズ（割当で省略すると 10000 ft）に落ちる。民間機の上昇・降下率は定数 1640 ft/min で、BADA のような高度スケジュール表はリポジトリに無い。通過高度はフィックス直上ではなく、最小 1.5 NM の fly-by 閾値で「離れ始めた点」で評価される。

本スライスは、制約を先読みし、機種上限内の必要上昇率・降下率でパスを組む。瞬間移動や上限を超える率は使わない。物理的に届かない制約は明示的にフラグする（API / レーダーラベルは足し算になるときだけ）。手続きに乗っていない航空機の運動はビット単位で変えない。

## 背景・課題

### 一次資料（FMS VNAV と管制官から見えるもの）

シミュレータの運動モデルは後述のとおり BADA 表ではない。以下は、誘導と「届かないとき」の表示を決めるための運航規則であり、性能数値の発明根拠ではない。

**ICAO Doc 4444（PANS-ATM）**

- 6.3.2.4.1 / 6.5.2.4.1: `CLIMB VIA SID TO (level)` / `DESCEND VIA STAR TO (level)` は、クリアされた高度まで上昇・降下し、**かつ** 公示された高度（および速度）制限と横方向パスに従うことを意味する。
- 6.3.2.3 Note 2 / 6.5.2.3 Note 2: SID / STAR の指定だけ（クリア高度が無い）では、プロファイル上昇・降下は許可されない。
- 第 12 章: 制限を守れない場合、乗員はできるだけ早く ATC に知らせる。用語は `UNABLE`、および `IF UNABLE (alternative) AND ADVISE`。ICAO の SID/STAR phraseology scenarios も「inform ATC as soon as possible」を繰り返す。

**ICAO Doc 8168（PANS-OPS）Vol. II**

- 手続き高度と SID の設計上昇勾配。特に指定が無ければ典型値は 3.3%（200 ft/NM）。より急な勾配は公示される。これは設計側の仮定であり、FMS が常にその勾配で飛ぶことではない。

**FAA AIM 5-2-9（Climb Via）/ 5-4-1（Descend Via）、Order 8260.46**

- 公示された高度・速度制限にすべて従う。"Expect" 高度は発出されない限り制限ではない。
- 米国の `CLIMB VIA SID` はトップ高度を省略できる場合があり、ICAO の `TO (level)` 必須とは異なる。本プロジェクトの対象は AIP Japan / ICAO 句なので、**クリア高度付きの Climb/Descend Via** を正とする。
- 守れないときは乗員が ATC に知らせる。
- 8260.46: 設計者は想定機が at-or-above を満たせるかを考慮し、必要上昇勾配を計算する（常に公示するとは限らない）。500 ft/NM を超える勾配は承認が要る。

**日本（管制方式基準 / AIM-J）**

- 管制方式基準は `CLIMB VIA SID TO [altitude]`（「SID又はトランジションの制限に従い〔高度〕まで上昇してください。」）と `DESCEND VIA STAR TO` を用いる（JAPA 資料が公式文言を引用）。
- AIM-J（AIM-Japan 編纂協会）は航空法・AIP・管制方式基準・飛行方式設定基準に基づく乗員向け手引である。本調査では AIM-J 全文の自由な取得はできなかった。管制側の一次条文としては管制方式基準の上記句を用いる。

**FMS の実務（規則から導く誘導。リポジトリの実装ではない）**

- 先読みして、今後の制約のうち最もきついものを、認証性能の範囲で満たす垂直パスを組む。
- 上昇では、途中の at-or-above を満たしたら、後続の AT / at-or-below / ウィンドウが水平飛行や幾何パスを要求しない限り、クリアされたトップに向けて上昇を続ける。
- 降下では at-or-below と AT のために TOD を計算し、早すぎる降下と遅すぎる降下の両方を避ける。
- 届かないときは FMS が annunciate し（例: UNABLE NEXT ALT）、乗員が ATC に `UNABLE` を伝える。管制官が見るのはその通報と、データブロックの leaving / climbing-to であり、黙って制約を破った機ではない。

### 現状（main `7bd7798`）の垂直モデル

リポジトリの民間機性能は **BADA 表ではなく**、`CommercialAircraft` の定数 `maxClimbRate = 1640` ft/min である（旋回 3°/s、加速 3 kt/s、速度 140–500 kt、天井 42000 ft）。`PositionUtils.calculateNextVerticalSpeed` は差が 50 ft 超ならこの上限、50 ft 以内で 10%、5 ft 以内で 0。`SIM_DELTA_SECONDS = 1.0` なので、1 ティックの最大変化は約 27.3 ft。

`WaypointAltitudeTargetResolver.resolveTarget` は **次のウェイポイントだけ** を見る。

- `AT_OR_ABOVE`: 現在高度が制約未満なら制約値、既に超えていれば現在高度を保持。
- `AT` / `AT_OR_BELOW` / `BETWEEN`: 制約値そのもの。
- 制約なし、または目標が null: `AircraftBase.resolveTargetAltitude` が `flightPlan.getCruiseAltitude()` に戻す。

`ProcedureFlightPlanMapper.DEFAULT_CRUISE_ALTITUDE_FT = 10000`。`POST .../assign-procedure` が `cruiseAltitude` を省略するとこの値が入る。#146 レビュー録画はスポーン時に 41000 等を置いても、割当時にクルーズを送らず 10000 に上書きしていた。

通過判定は、対地速度 × 5 秒を 1.5–5.0 NM にクランプした動的閾値の内側に入り、かつフィックスから離れ始めた点。高度はこの点で評価され、フィックス直上（abeam）ではない。`satisfiesConstraintAtPass` の許容は `AT_OR_ABOVE` / `AT_OR_BELOW` が 100 ft、`AT` / `BETWEEN` が 500 ft。満たさないとインデックスを進めないが、100 ft は数十フィートの不足を隠す。#146 レビューはさらに緩い ±250 / ±400 ft だった。

### 課題（Problem Statement）

- 公示 at-or-above / ウィンドウ（上昇）と at-or-below / AT（降下）を、機種が届くときに満たさない。
- 目標が「次のフィックス」に閉じているため、制約の無い中間フィックスでクルーズへ降下し、後続の上昇制約の開始が遅れる。降下の TOD も組まない。
- 届かない制約を `UNABLE` 相当として表面化せず、許容差の内側に隠すか、黙って不足したまま通過する。
- レビュー許容 ±250 ft を「満たした」と読んではならない。

### なぜ今か（Motivation）

#146 で 114 本が割り当て可能になった。垂直パスが制約を満たさなければ、カタログを増やしても SID / STAR の訓練・管制として使えない。KAMAT の 63 ft 不足は単発の丸めではなく、同じモデルがスライス 1・3 の広域スイープで繰り返す。次の実装単位として、先読み誘導と到達不能フラグを入れる。

### KAMAT が見逃された理由（`TIARA3B.RWY16R`）

スイープと #146 録画（`flight-12plus.json`）は一致する。開始 300 ft、`t = 316` s、高度 **8937.33 ft**、フィックスまで 0.992 NM、制約 `AT_OR_ABOVE 9000`。

1. **上昇率モデル（直接因の半分）**。定数 1640 ft/min を 316 秒維持すると `300 + 1640 × 316 / 60 = 8937.33` ft で、9000 ft まであと 63 ft（約 2.3 秒）。T6R13 / HATBA / KAMAT までのトレースは上限上昇のままである。BADA のような高度別 ROC は使っていない。
2. **通過点（直接因のもう半分）**。高度は fly-by 開始（0.992 NM）で評価される。残り約 0.99 NM を同じ 1640 ft/min で飛べば 9000 ft には届く見込みが大きい。LAYER（12935 vs 13000、-65 ft）と GUSRO（16958 vs 17000、-42 ft）も同じ「上限上昇＋評価点」の級である。
3. **目標選択 / 先読み不足は、この 63 ft の直接因ではない。** KAMAT 時点では既に 9000 / 10000 に向けて上限上昇している。**別件として深刻なのは**、LAYER の次の TIARA に制約が無いため目標がクルーズ 10000 に戻り、LAYER 12935 ft から TIARA 10338 ft へ降下してから、GUSRO の `+FL170` へ再び上昇することである。

結論: KAMAT は「先読みしていなかったから 63 ft 足りない」のではなく、**定数上昇率と fly-by 評価点**の組み合わせである。先読み欠如は、中間降下と後続制約の開始遅れとして、同じ便（および多数の SID）で別に現れる。

分類（実装で直す対象）:

1. **上限上昇率＋ fly-by 評価点** — KAMAT 型。次制約に向け既に上限上昇しているが、評価点で数十フィート足りない。1640 ft/min を無断で上げず、評価点までに届くよう（必要ならもう少し早く上限を維持し、許容は 50 ft より緩くしない）満たす。残り距離を「無料の高度」としてテレポートしない。
2. **先読み不足 / クルーズ 10000 へのフォールバック** — RAMBA・HANAR・LAYER 後の TIARA 降下。制約の無い次フィックスや、クリア高度より低いデフォルトクルーズを、上昇中の目標にしてはならない。
3. **降下 TOD の欠如** — STAR の AT（EPSON 等）。後続の AT / at-or-below / ウィンドウに対し、上限内の必要降下率で TOD を置く。
4. **開始条件つき到達不能** — POLIX AT 15000 のように、IF 上 16000 ft・1640 ft/min・現行の通過判定では物理的に足りない場合。黙って不足させずフラグする。1640 を「実機らしい値」へ書き換えて消さない。

## 方針

### 決定方針（Decision）

1. **型を先に固定する。** 高度制約は `VerticalConstraint` のユニオン（sealed type / 同等の明示的直和）にする。少なくとも `none` / `at(altitude)` / `atOrAbove(altitude)` / `atOrBelow(altitude)` / `window(min, max)`。高度はフライトプラン上のフィート、カタログ上は既存どおり `ft` または `{constraint, fl}`。既存の `AltitudeConstraint` 列挙と `ProcedureAltitude` は、このユニオンへ写像する（破壊的に捨てる必要は無い）。誘導やスイープを書く前に型と写像のテストを通す。
2. **制約先読みの垂直誘導。** 乗務中の手続きレグ列を先読みし、次に効く制約（およびクリア高度）から、評価点までに必要な上昇率・降下率を求める。上昇では、途中の at-or-above を満たしたあと、後続の AT / at-or-below / ウィンドウが要求しない限り、クリアされたトップへ上昇を続ける。降下では AT / at-or-below / ウィンドウの TOD を置く。目標は「次のフィックスが制約なしだからクルーズへ戻す」ではない。
3. **機種性能の内側だけを使う。** 率の上限は現行の `AircraftCharacteristics.maxClimbRate`（民間機 1640 ft/min）である。必要率が上限以下ならその率（または上限）で届ける。上限を超える率、高度の跳び、フィックスへの瞬間移動は禁止する。BADA 表や「実機の典型 ROC」を発明して 1640 を上げない。性能モデルを置き換えるのは別スライスである。
4. **クリア高度（Climb/Descend Via TO）を垂直パスの天井・床として扱う。** フライトプランのクルーズがクリア高度である。割当でクルーズが省略された SID では、デフォルト 10000 ft を理由に、より高い公示 at-or-above のあいだで降下して戻してはならない。実装は次のいずれか（または同等）とし、10 分サンプルの既存断言を壊さない範囲で選ぶ。(a) 省略時のクリア高度を、パス上の最も高い AT / AT_OR_ABOVE / ウィンドウ上端以上にする（変更はマッピングに閉じ、グローバル定数の無断変更でサンプルを壊さない）。(b) デフォルト 10000 を維持する場合でも、上昇中に制約なしフィックスで 10000 へ降下せず、クリア高度より上の公示制約は到達不能（クリア不足）としてフラグする。ICAO では SID 指定だけではプロファイル上昇は許可されない。
5. **物理的に届かない制約は明示する。** 「評価点までの距離と残高度に対し、機種上限率でも間に合わない」（およびクリア高度より上の制約で、クリアを上げない方針を採った場合）をドメイン状態として持つ。API やレーダーラベルへの投影は、既存の応答・ラベルに**足す**ときだけ行う。既存フィールドの意味を上書きしない。管制官向けの意味は `UNABLE`（乗員が知らせる）とデータブロックであり、黙った制約破りを「満たした」と表示しない。音声発出や無線フレーズの自動送信は範囲外。
6. **通過評価は現行の横方向通過点を正とする。** フィックス直上へ評価点を移すのは横方向の変更になり、本スライスの必須ではない。垂直パスは、現行の fly-by / 「離れ始め」点で制約を満たすように組む。許容差は隠しには使わない（後述）。
7. **手続きに乗っていない航空機はビット単位で同一。** 手続きルートを割り当てていない機、`DIRECT_TO` / `HOLDING` / 指示高度だけの機の垂直運動は、本スライス前後で一致する。

### 検討した他案（Alternatives Considered）

| 案 | 内容 | 判断 |
|---|---|---|
| A. 制約先読み＋上限内の必要率＋到達不能フラグ（採用） | 規則上の Climb/Descend Via に近く、既存の 1640 ft/min を発明でいじらない。 | 採用。 |
| B. 上昇率を「ジェットらしい」値（例: 2000–3000 ft/min）に上げて KAMAT を消す | 63 ft は消えるかもしれないが、モデル根拠が無く、中間降下は残る。 | 却下。リポジトリに BADA 表は無い。 |
| C. 通過判定だけをフィックス直上に移す | KAMAT は届く見込みだが、先読み不足とクルーズフォールバックは残る。横方向の回帰範囲が広い。 | 本スライスでは採らない（将来の通過幾何の課題として範囲外に残す）。 |
| D. `satisfiesConstraintAtPass` の 100 ft やレビューの 250 ft を広げて「満たした」ことにする | 証拠を隠すだけ。 | 禁止。 |
| E. 次フィックス制約に届かないときだけ高度を制約値へスナップする | テレポート。 | 禁止。 |
| F. 誘導は現状のまま、API に不足フラグだけ足す | 届く制約まで「届かない」と出る。 | 却下。先に届くものは届ける。 |

### トレードオフ（Trade-offs）

- **メリット**: 公示制約を、機種が届くときに満たす。中間の不当な降下を止める。届かないものは管制官／API から見える。
- **デメリット / 受容する制約**: 1640 ft/min の定数モデルでは、開始条件や間隔によっては本当に届かない制約が残る。それを性能の書き換えて消さない。クリア高度の省略時ルールは、10 分サンプルを壊さないように選ぶ。通過点を fly-by のままにするので、直上なら足りる不足は、評価点で足りるパスを組むか、到達不能として扱う。

## 完了条件（Success Criteria）

1. **型が先。** `VerticalConstraint` ユニオン（または同等の直和）と、カタログ / `FlightPlanWaypoint` からの写像テストが、誘導変更より先に存在する。`AT` / `AT_OR_ABOVE` / `AT_OR_BELOW` / ウィンドウ / なし、および `ft` と `fl` の既存マッピング（フライトプランは FL×100 ft。カタログの `{constraint, fl}` は壊さない）をカバーする。
2. **広域スイープテストが、届く制約について許容内のミス 0 を断言する。** 対象はスライス 3 の割り当て可能 107 本＋掲載トランジション、およびスライス 1 の 15 STAR＋VAMOS 滑走路系と掲載トランジション（本ドラフトの 195 便と同等）。開始条件をテストに明示する。**許容は `AT_OR_ABOVE` / `AT_OR_BELOW` で 50 ft（片側。現行の 50 ft キャプチャ帯。1 ティック 27.3 ft より広く、現行ドメイン 100 ft より狭い）、`AT` / ウィンドウで 100 ft。** 63 ft の KAMAT 不足は不合格のまま残してはならない。レビューの ±250 ft は使わない。物理的に届かない制約はミスとして失敗させず、到達不能フラグ付きであることを断言する（POLIX 型など、テストが「届かない」と分類したもの）。
3. **10 分サンプルの既存ガードを変更しない。** `QuickstartStarScenarioIntegrationTest` と `QuickstartDepartureScenarioIntegrationTest` はテストコードを触らず、実装後も通る。
4. **手続きに乗っていない航空機の運動はビット単位で同一。** 既存の無風キネマティクス金を含む、手続き外の垂直パス回帰が、本スライスの差分前後で一致する。手続き機だけが新しい誘導を使う。
5. **README**（必要なら Backend README の手続き説明）に、SID/STAR 機が公示高度制約を機種上限の範囲で満たすこと、届かない制約はフラグすること、出典一行を書く。UI に「運航に使えない」バナーは出さない。出典は従来どおり次の一行だけである。

6. **範囲外リスト**（次節）が実装 PR に残っている。

## 影響範囲

- **型**: `VerticalConstraint` 新規（または `AltitudeConstraint` / `ProcedureAltitude` の写像層）。フライトプランとカタログの既存 JSON 契約は壊さない。
- **誘導**: `WaypointAltitudeTargetResolver`、`AircraftBase.resolveTargetAltitude`、必要なら垂直速度の目標レート（上限内）。`CommercialAircraft` の 1640 ft/min 定数そのものは、性能モデル置換が無い限り変えない。
- **割当マッピング**: クルーズ省略時のクリア高度（上記方針 4）。`DEFAULT_CRUISE_ALTITUDE_FT` を無断で全域変更してサンプルを壊さない。
- **到達不能フラグ**: ドメイン状態。API / ラベルは加法的なときだけ。
- **テスト**: 新規スイープ（受け入れ）。既存 10 分サンプルは不変更。手続き外金は不変を確認。
- **README**: 上記の短い説明と出典一行。
- **触れないもの**: `waypoints.json` の既存座標、スライス 1 JSON、スライス 2 出発サンプル、既定到着クイックスタート、UI 警告バナー、速度制約の自動遵守、公示上昇勾配の自動適用、ホールド自動進入。

## 実装計画

### Phase 1（Must: 型）

- `VerticalConstraint` ユニオンと写像、単位テスト。誘導はまだ変えない。

### Phase 2（Must: 先読み誘導）

- 次に効く制約とクリア高度から、現行通過点までの必要 ROC / ROD を計算する。
- 上昇継続（中間 at-or-above のあとにクルーズへ降ろさない）、降下 TOD。
- 率は `maxClimbRate` でクリップ。クリップしても届かない場合はフラグし、上限率のまま飛ばす（足りない高度を足さない）。
- クルーズ省略時ルールを方針 4 どおり実装し、10 分サンプルで確認する。

### Phase 3（Must: 受け入れテストと文書）

- 195 便相当のスイープを恒久テストにする。届く制約は許容内ミス 0、届かない制約はフラグ。
- 手続き外のビット同一を回帰。
- README と範囲外リスト。

### Phase 4（加法的なら: API / ラベル）

- 到達不能を既存の航空機・割当レスポンスにフィールド追加する、またはレーダーラベルに短い印を足す。未使用ならドメインフラグだけでも完了条件 2 は満たせるが、足すなら加法のみ。

## 範囲外（Out of scope）

- 民間機 1640 ft/min を、文書化された性能モデル無しに引き上げること。BADA 表の新規導入。
- 高度のスナップ、テレポート、上限超過の率。
- 通過判定をフィックス直上へ移すこと（横方向の別課題）。
- 速度制約（パス表 KIAS）の自動遵守、公示上昇勾配（ft/NM）の自動適用。
- 公示ホールドの自動進入（スライス 1・3 と同じ）。
- `UNABLE` の音声・無線自動発出、チャットへの自動送信。
- UI の「運航に使えない」警告バナー。出典は README とデータファイルの一行のみ。
- `waypoints.json` の既存座標の上書き、スライス 1 JSON の編集、スライス 2 出発サンプル、既定到着クイックスタート。
- 10 分サンプル・テストの改変。
- 手続きに乗っていない航空機の垂直運動の変更。
- FL の QNH 真高度化（フライトプラン写像は従来どおり FL×100 ft）。

## 未解決事項（Unresolved Questions）

- 割当 API がクルーズを省略したとき、クリア高度を「パス上の最高上昇制約以上」へ上げるか、10000 ft のまま「制約がクリアより上ならフラグ」にするか。10 分サンプルを壊さない方が勝つ。実装 PR で一方を選び、README に一行書く。
- STAR のスイープ開始を IF 上 16000 ft とするのは、#146 レビュー録画と揃えた仮定である。製品のスポーン高度が異なるなら、スイープの開始を製品に合わせ、到達不能の分類を再計算する。
- 到達不能フラグを最初の PR で API / ラベルに出すか、ドメインのみにするか。加法的なら出してよい。必須はドメインで明示することである。
